# ADDENDUM TO v3.3: THE EXECUTION LAYER (v3.4)

## Section 33: Rejection Counter Framework ("If They Balk" Protocol)

### 33.1 Overview

The decision trees treat "negotiation fails" as a terminal branch outcome. But real negotiations rarely fail at a single stroke — they fail through a *sequence of unhandled rejections*. This section specifies the system for responding to rejection *within* the live interaction, before the branch resolves.

**Research foundation:** Ury's five-step breakthrough strategy (Getting Past No, 1991) is the canonical framework; supplemented by Schelling's commitment/threat analysis (1960), Cialdini's influence principles (2009), and Rapoport's conflict de-escalation research.

### 33.2 The Rejection Taxonomy

Every rejection encountered during execution is classified into one of eight types. Each type has a distinct underlying meaning, and **applying the wrong counter to the wrong rejection type escalates failure**:

```python
class RejectionType(Enum):
    HARD_NO = "hard_no"                    # "That's not possible. Final answer."
    SOFT_NO = "soft_no"                    # "Hmm, I don't think that works for us..."
    LOWBALL_COUNTER = "lowball_counter"    # Counter far below your ask
    CONDITIONAL_NO = "conditional_no"      # "Not unless you X" (= opening, not rejection)
    STALLING = "stalling"                  # Silence, delay, non-response
    AUTHORITY_DEFLECTION = "authority"     # "I'd have to check with my boss/committee"
    TAKE_IT_OR_LEAVE_IT = "ultimatum"      # "This is the offer. Yes or no."
    RELATIONAL_PRESSURE = "relational"     # "After everything we've done for you..."


class RejectionClassifier:
    """
    Classifies live rejection into taxonomy, because the
    correct counter depends on rejection TYPE, not just content.
    
    Research: rejection type predicts which response de-escalates
    vs. escalates (Pruitt & Carnevale, 1993 — Negotiation in
    Social Conflict).
    """
    
    LINGUISTIC_MARKERS = {
        RejectionType.HARD_NO: [
            "not possible", "final answer", "absolutely not",
            "out of the question", "we can't do that", "that's firm"
        ],
        RejectionType.SOFT_NO: [
            "i don't think", "that might be difficult", "hmm",
            "not sure that would work", "that could be tricky",
            "we'd have to see"
        ],
        RejectionType.LOWBALL_COUNTER: [
            # Detected by counter-value ratio, not language
            # See _is_lowball below
        ],
        RejectionType.CONDITIONAL_NO: [
            "unless", "if you can", "provided that", "on the condition",
            "only if", "what if you"
        ],
        RejectionType.STALLING: [
            "let me think about it", "i'll get back to you",
            "need to consider", "give me some time",
            # Or: detected via non-response over threshold time
        ],
        RejectionType.AUTHORITY_DEFLECTION: [
            "my boss", "the committee", "above my pay grade",
            "i'd have to ask", "the team decides", "procurement"
        ],
        RejectionType.TAKE_IT_OR_LEAVE_IT: [
            "take it or leave it", "this is the offer", "yes or no",
            "non-negotiable", "that's our position"
        ],
        RejectionType.RELATIONAL_PRESSURE: [
            "after all we've", "we've been so good", "i thought we",
            "loyalty", "we've invested", "you owe"
        ],
    }
    
    def classify(self, rejection_text: str, context: dict) -> 'ClassifiedRejection':
        """Classify rejection; detect lowball via counter/ask ratio."""
        
        # Linguistic classification first
        for rtype, markers in self.LINGUISTIC_MARKERS.items():
            for marker in markers:
                if marker in rejection_text.lower():
                    return ClassifiedRejection(
                        type=rtype,
                        text=rejection_text,
                        confidence=0.85,
                        linguistic_trigger=marker
                    )
        
        # Lowball detection: counter-value analysis
        if "counter_value" in context and "ask_value" in context:
            ratio = context["counter_value"] / context["ask_value"]
            if ratio < 0.70:  # Counter below 70% of ask
                return ClassifiedRejection(
                    type=RejectionType.LOWBALL_COUNTER,
                    text=rejection_text,
                    confidence=0.80,
                    ratio=ratio,
                    note=f"Counter is {ratio:.0%} of ask"
                )
        
        # Default: soft no (most ambiguous category)
        return ClassifiedRejection(
            type=RejectionType.SOFT_NO,
            text=rejection_text,
            confidence=0.40,
            note="No clear marker; classified as ambiguous soft no"
        )
```

### 33.4 Integration with Existing Systems

```
INTEGRATION POINTS:

1. DECISION TREE: Each counter tactic that creates new terms
   (component splits, conditional acceptances) generates a new
   branch in the existing Phase 3 tree → runs through existing
   minimax solver → user knows the EV of each counter before
   deploying it.

2. LEVERAGE MAP: Credibility assessments (ultimatum protocol)
   read from and update the counterparty's leverage assessment.

3. CLAIM CLASSIFICATION (§9): Every counter recommendation is
   itself classified. E.g., "silence mirroring" = PRACTITIONER_
   HEURISTIC (0.45), "interest inquiry" = VALIDATED_RESEARCH
   (Ury framework, 0.80).

4. BASE RATES (§12): No base rates for rejection outcomes —
   counters are tactical choices, not statistical predictions.
   System does NOT claim "this counter works X% of the time."

5. EV ENFORCEMENT (§11): Conditional acceptances and component
   splits are run through EV calculation before recommendation —
   contingent counter-gains are probability-weighted.
```

## Section 34: BATNA Deployment System

### 34.1 The Gap This Closes

The leverage strategy says *"Mention your alternatives."* But **mentioning is not deploying**. The system currently tells the user WHAT they have (BATNA strength 4.2) without telling them HOW to use it. Deploying a BATNA badly is worse than not deploying it:

```
❌ BAD DEPLOYMENT: "I have another offer, so you'd better improve this one."
   → Reads as threat, triggers defensive escalation, burns goodwill

❌ BAD DEPLOYMENT: Revealing BATNA too early, before it's fully developed
   → Counterparty calls the bluff or waits for it to expire

❌ BAD DEPLOYMENT: Revealing specifics that can be matched or sabotaged
   → "Oh, that company? We know their budget is capped at..."
```

### 34.2 The BATNA Revelation Ladder

The core structure: BATNA deployment is a **seven-level escalation ladder**. Each level reveals more, risks more, and commits more. The system recommends a level based on context; the user controls actual deployment.

**Research foundation:** Schelling (1960) on threat vs. warning distinction; Spence (1973) on costly signaling; Akerlof (1970) on information revelation under asymmetry; Cialdini (2009) on scarcity.

        - BATNA strength (from leverage map)
        - BATNA development status (is it real? verified?)
        - Negotiation stage (early/middle/late)
        - Current terms vs. reservation point (are we above floor?)
        - Relationship value (high-value relationships bias toward lower levels)
        - Counterparty response pattern so far
        """
        
        batna = leverage_map.get_leverage_by_type("BATNA")
        if not batna or batna.strength < 3.0:
            return {
                "level": 0,
                "reason": "BATNA weak or undeveloped. Revealing weakness "
                         "is worse than silence. Recommendation: develop "
                         "BATNA before deployment.",
                "development_advice": "Level 0 while building alternatives "
                                     "(follow up with recruiters/other "
                                     "options first — per batna_theory: "
                                     "improve BATNA before negotiating)"
            }
        
        # Strong BATNA exists — calibrate by stage and gap
        current_terms = context.get("current_terms_utility")
        reservation = context.get("reservation_point_utility")
        gap = current_terms - reservation
        
        if gap > 0.2:
            # Current terms well above floor — BATNA as gentle pressure
            return {"level": 1, "reason": "Terms above reservation; "
                    "BATNA as ambient pressure, not weapon"}
        elif gap > 0:
            # Terms near floor — increasing pressure warranted
            return {"level": 2, "reason": "Terms approaching reservation; "
                    "categorical existence signals seriousness"}
        elif gap <= 0:
            # Terms at/below floor — decision territory
            if batna.strength >= 4.0 and batna.user_aware:
                return {"level": 5, "reason": "Terms below reservation "
                        "with strong BATNA — activation signal warranted "
                        "(warning-framed)", "gate_check": True}
            else:
                return {"level": 3, "reason": "Terms below reservation "
                        "but BATNA not fully verified — specific reference "
                        "to pressure-test before activation"}
        
        return {"level": 1}

### 34.3 The Warning-vs-Threat Grammar

This is the core linguistic distinction that prevents BATNA deployment from backfiring:

```
┌─────────────────────────────────────────────────────────────┐
│  SCHELLING'S DISTINCTION, OPERATIONALIZED                    │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  WARNING (preserve relationship + credibility):              │
│  ├── Contingency attributed to EXTERNAL circumstances        │
│  ├── "The other option has a deadline attached..."           │
│  ├── "I'll need to respond to them by [date]..."             │
│  ├── Stated preference for current deal preserved            │
│  │   ("I'd prefer this one — that's why I'm here")          │
│  └── Counterparty retains agency (they choose)               │
│                                                              │
│  THREAT (create confrontation, require commitment):          │
│  ├── Contingency attributed to YOUR choice                   │
│  ├── "If you don't improve this, I'll take the other one"   │
│  ├── "You need to do better or I walk"                       │
│  ├── Preference structure erased (deal = hostage)           │
│  └── Counterparty's face is at stake → defensive escalation  │
│                                                              │
│  THE SAME BATNA, TWO GRAMMARS:                               │
│                                                              │
│  ❌ Threat: "I have another offer, so if you can't get to    │
│     $95k, I'll have to take it."                            │
│     → Confrontational, commitment-forcing, relationship cost │
│                                                              │
│  ✅ Warning: "I want to flag that the other option needs a   │
│     decision by Friday — I'm telling you because I'd        │
│     rather make this work. What's possible on your end?"    │
│     → Informational, agency-preserving, face-preserving,    │
│       preference-affirming                                  │
│                                                              │
│  SYSTEM RULE: All generated BATNA language uses WARNING      │
│  grammar. THREAT grammar only if user explicitly chooses     │
│  confrontation (and system logs the choice + risks).         │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```
